# 边缘AI作业工时测定系统 -- AI团队专业工作流

> 版本：1.2 | 设计者：软件架构师 + 项目经理 | 日期：2026-04-02
> 状态：已接受 | 适用范围：全AI团队（软件架构师、项目经理、后端架构师、后端开发工程师、前端开发者、审查专家、运维）

---

## 1. 核心理念

本项目所有代码均由AI编写，角色之间通过session切换协作。信息的传递完全依赖文件系统，因此必须建立严格的、可追溯的、自文档化的工作流。

设计原则：
- 文件即契约：技术决策、任务分配、审查结果以文件沉淀
- 角色隔离：每个角色只在自己的能力域内操作
- 规范先行：开发前先出spec，开发后做review，形成闭环
- 记忆同步：每个session结束后更新工作记忆
- 用户是决策者：关键决策由用户拍板

## 2. 团队角色（7个）

| 角色 | 核心职责 | 能力域 | 不做什么 |
|------|---------|--------|---------|
| **软件架构师** | 技术选型、系统设计、接口规范制定、模块划分、架构问题裁决、技术研究报告 | specs/、全局架构设计 | 不做项目管理、不写业务代码、不做代码审查 |
| **项目经理** | Phase规划、任务分工、进度跟踪、质量裁决、跨模块协调、用户沟通 | phase<N>_plan.md、phase<N>_task_assignment.md | 不做技术决策、不写代码、不做代码审查 |
| **后端架构师** | 基础设施集成、数据链路设计、实时推送、中间件对接（Redis/InfluxDB/WebSocket/SSE/Celery） | app/core/, app/perception/, app/services/stream*, app/api/websocket, app/api/sse | 不碰业务CRUD、不碰前端 |
| **后端开发工程师** | 业务数据模型、CRUD API、Dashboard/LineBalance等业务逻辑 | app/models/, app/api/v1/（业务路由）, tests/ | 不碰基础设施层、不碰前端 |
| **前端开发者** | 前端功能实现、UI组件、API对接、实时化改造、前端测试 | mes-frontend/src/, mes-frontend/tests/ | 不碰后端代码、不定义后端规范 |
| **审查专家** | 代码质量审计、安全审计、测试覆盖评估 | 全部源代码（只读） | 不改代码、不做架构决策 |
| **运维** | Docker编排、部署配置、nginx反向代理、环境管理 | Dockerfile*, docker-compose*, docker/, .env* | 不改业务代码 |

### 2.1 架构师与项目经理的职责边界

原"总设计师"同时承担技术架构决策和项目管理协调，职责过重且思维模式不同，现拆分为两个独立角色：

**软件架构师**是技术的最终决策者，负责"怎么设计"。典型任务包括：
- 系统架构设计（模块划分、数据流、部署架构）
- 技术选型（框架、中间件、数据库、AI模型）
- 制定技术规范（specs/ 下的 spec_*.md）
- 接口契约定义（API格式、命名规范、协议选择）
- 架构问题裁决（当审查发现架构层面问题时出方案）
- 技术研究报告（research_report_*.md）
- 审查规范的 spec 未覆盖问题时补充 spec

**项目经理**是流程的把控者，负责"怎么推进"。典型任务包括：
- Phase 规划（phase<N>_plan.md）
- 任务分工（phase<N>_task_assignment.md）
- 进度跟踪和依赖管理
- 质量裁决（决定哪些审查问题必须在当前Phase修复）
- 跨模块协调（前后端接口对齐、共享文件冲突等）
- 用户沟通（需求确认、阶段验收、风险预警）

### 2.2 架构师与项目经理的协作规则
- 需求分析阶段：项目经理主导用户沟通，架构师评估技术可行性，两者共同产出需求结论
- 规范制定阶段：架构师出spec，项目经理确认spec的优先级和排期
- 任务分工阶段：项目经理拆解任务，架构师确认任务的技术依赖关系
- 审查修复阶段：审查专家发现架构问题 -> 架构师裁决方案 -> 项目经理安排修复排期
- 阶段验收阶段：项目经理汇总进度，架构师汇总技术成果，共同向用户汇报

### 2.3 后端两个角色的职责边界

项目将后端拆分为"架构师"和"开发工程师"两个角色，原因是后端的职责范围差异很大：

**后端架构师**负责"管道"——数据从哪来到哪去、中间件怎么对接、基础设施怎么集成。典型任务包括：
- Redis/InfluxDB客户端封装（app/core/redis_client.py, app/core/influxdb_client.py）
- Stream消费者服务（app/services/stream_consumers.py）
- 感知进程适配器（app/perception/redis_adapter.py）
- WebSocket/SSE端点（app/api/websocket.py, app/api/sse.py）
- Lifespan集成（main.py中的启动顺序）
- Celery异步任务框架（Phase 4+）

**后端开发工程师**负责"业务"——具体功能逻辑和数据模型。典型任务包括：
- SQLAlchemy数据模型（app/models/database.py）
- Pydantic schema（app/models/schemas.py）
- 业务CRUD API（orders, customers, inventory, equipment, reports, auth）
- Dashboard/LineBalance业务API
- 业务相关测试

### 2.2 两个后端角色的协作规则

- 架构师的基础设施（Redis/InfluxDB）是开发工程师的依赖——先架构后业务
- 开发工程师的API需要调用架构师的客户端——通过spec对齐接口
- 两者共享 main.py——架构师负责lifespan集成，开发工程师负责路由注册，合并由总设计师协调
- 审查时按能力域分配修复任务：基础设施问题 -> 架构师，业务逻辑问题 -> 开发工程师

## 3. Phase生命周期（7阶段）

```
需求分析 -> 规范制定 -> 任务分工 -> 开发执行 -> 代码审查 -> 修复验证 -> 阶段验收
```

### 3.1 需求分析

执行者：用户 + 项目经理 + 软件架构师

1. 用户描述需求目标
2. 项目经理分析工作量、排期、资源影响
3. 软件架构师评估技术可行性、架构兼容性
4. 用户确认方向后进入规范制定

### 3.2 规范制定

执行者：软件架构师

1. 根据需求制定技术规范，存入 `specs/`
2. 规范必须包含：接口契约、命名约定、行为约定、安全约束
3. 涉及前后端对接时，必须同时定义API的request/response格式
4. 文件命名：`spec_<主题>.md`
5. 文件头部标注版本号和状态（草案/已接受/已废弃）

### 3.3 任务分工

执行者：项目经理（软件架构师确认技术依赖）

1. 将规范拆解为可执行任务
2. 按角色能力域分配
3. 明确依赖关系、执行顺序、验收标准
4. 产出文件：`phase<N>_task_assignment.md`

### 3.4 开发执行

执行者：后端架构师 / 后端开发工程师 / 前端开发者 / 运维

1. 读取任务分工文档和相关spec
2. 按依赖顺序逐个完成任务
3. 每完成一个任务：运行测试、更新进度、记录决策
4. 禁止：硬编码数据、使用emoji、越过spec自行决策

### 3.5 代码审查

执行者：审查专家

1. 对本次Phase新增/修改的代码进行全面审查
2. 审查维度：功能正确性、代码质量、安全性、测试覆盖、架构一致性
3. 产出文件：`code_review_report_<模块>_<日期>.md`
4. 问题按严重程度分级（Critical/High/Medium/Low）

### 3.6 修复验证

执行者：对应开发者角色（按能力域分配），由项目经理安排优先级

1. 项目经理评估审查报告，确定修复优先级和排期
2. 切换到对应开发者session执行修复
3. 架构问题由软件架构师裁决方案后再修复
4. 每修复一个问题，跑全量测试确认无回归
5. 可选：再次启动审查验证

### 3.7 阶段验收

执行者：用户 + 项目经理 + 软件架构师

1. 项目经理汇总Phase进度（任务完成情况、审查修复状态）
2. 软件架构师汇总技术成果（新增文件、测试结果、资源预算、架构影响）
3. 用户决定通过或需要补充
4. 更新长期记忆

---

## 4. 审查分级标准

| 级别 | 定义 | 必须修复 |
|------|------|---------|
| Critical | 安全漏洞、数据丢失风险、核心功能错误 | 是 |
| High | 性能问题、功能不完整、违反spec | 是 |
| Medium | 代码质量、可维护性、防御性编程缺失 | 建议 |
| Low | 命名规范、格式建议、文档缺失 | 可选 |

## 5. 角色切换协议

### 切换前（当前角色）
- 完成收尾工作
- 更新工作记忆
- 标注未完成任务进度
- 向用户汇报当前状态

### 切换后（新角色）
- 读取长期记忆（`.workbuddy/memory/MEMORY.md`）
- 读取任务分工文档
- 读取相关技术规范
- 如果是修复任务，读取审查报告
- 不假设，以文件为准

## 6. 特殊场景

### 紧急Bug修复
Critical/High -> 直接指派修复 -> 审查验证
Medium/Low -> 记录到Bug列表，下Phase安排

### 架构调整
软件架构师输出研究报告 -> 用户决策 -> 项目经理排期 -> 按Phase流程执行

### 规范冲突
代码问题 -> 修复流程
spec不合理 -> 审查专家标注 -> 软件架构师评估 -> spec更新 -> 代码适配

### 跨模块问题
审查专家标注 -> 软件架构师裁决技术方案 -> 项目经理协调排期 -> 分别指派前后端 -> 集成验证

|--------|------|------|

| 审查修复 | 无回归 | 无回归 |

## 8. 项目文档体系

| 文档类型 | 存放位置 | 命名规范 | 维护者 |
|---------|---------|---------|-------|
| Phase计划 | 项目根目录 | `phase<N>_plan.md` | 项目经理 |
| 任务分工 | 项目根目录 | `phase<N>_task_assignment.md` | 项目经理 |

| 工作流规范 | `specs/` | `spec_workflow.md`（本文件） | 软件架构师 + 项目经理 |
| 审查报告 | 项目根目录 | `code_review_report_<模块>_<日期>.md` | 审查专家 |
| Bug修复报告 | 项目根目录 | `bug_fix_report_<日期>.md` | 修复者 |
| 研究报告 | 项目根目录 | `research_report_<主题>.md` | 软件架构师 |
| 工作记忆 | `.workbuddy/memory/` | `YYYY-MM-DD.md` / `MEMORY.md` | 全体 |

## 9. 执行检查清单

### Phase开始前（项目经理 + 软件架构师）
- [ ] 需求已明确且用户已确认（项目经理）
- [ ] 相关技术规范已制定或已存在（软件架构师）
- [ ] 任务分工文档已输出（项目经理）
- [ ] 每个任务有明确验收标准（项目经理）
- [ ] 任务依赖关系已梳理（项目经理 + 软件架构师）
- [ ] 资源预算已评估（软件架构师）

- [ ] 已读取任务分工文档
- [ ] 已读取相关技术规范
- [ ] 已读取长期记忆了解项目约定
- [ ] 理解验收标准

### 审查开始前（审查专家）
- [ ] 已明确审查范围
- [ ] 已读取相关技术规范
- [ ] 审查维度已确认
